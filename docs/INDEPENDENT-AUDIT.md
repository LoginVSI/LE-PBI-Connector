## Runtime and acceptance limits

The elapsed guard is cooperative and uses a wall clock, not a monotonic clock. It starts when the first request forces the context deadline, which is shared by that connector evaluation. It cannot preempt an in-flight request, JSON decoding, lazy table transformations or Desktop work. A request started before expiry can run up to its own 30-second timeout; decoding/engine work can extend that further. Host clock changes can affect it. Separate connector evaluations, previews, tables or refreshes can have separate budgets. This is **not a hard overall refresh deadline**. Request timeout, retry count and page caps remain independent bounds. Narrow the window after a budget failure; never publish partial data.

Offset pagination is not a snapshot. Mutable data or equal sort keys can still shift between requests; totals and repeated-page checks cannot prove there are no omissions. Run queries now use immutable `created` sorting; configuration routes use the contract's name sort. Reconcile stable, completed windows and compare IDs when accepting large results. Measurements have no unique observation ID in this contract; no speculative deduplication was added. Per-day half-open filtering prevents midnight duplication. Sessions spanning days deliberately appear in both interval views: count distinct session IDs across their union, not summed window counts. Their active-interval grain cannot be reconciled as a count of point observations.

Table datetime columns retain refreshing-machine local conversion for customer compatibility; acquisition and point filtering operate in UTC before that conversion. Local/DAX date filters can therefore differ from the UTC input window. Tests cover explicit offsets and UTC DST windows, but do not emulate a Desktop timezone change. Finished runs overlapping multiple report windows are interval-selected; their run counts also cannot be summed as incremental ingestion.

No Desktop process was launched, installed, restarted or controlled. No DAX engine, gateway or Service acceptance is claimed. The PBIT is structurally derived: opening, rendering, interaction behavior and save/reopen remain required. See [ACCEPTANCE.md](ACCEPTANCE.md), including model-level queries and edge cases. Weighting is deferred until the population of each count is known. Licence ownership and historical credential revocation remain owner actions. Gateway, scheduled refresh and incremental ingestion stay in the backlog.

References for supported mechanisms: [Microsoft clock functions](https://learn.microsoft.com/en-us/powerquery-m/m-local-fixed-utc-variants), [manual credential handling](https://learn.microsoft.com/en-us/power-query/handling-authentication), [Web.Contents request timeout](https://learn.microsoft.com/en-us/powerquery-m/web-contents).
